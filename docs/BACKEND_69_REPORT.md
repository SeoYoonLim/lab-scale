## 1. 69-A 문제 원인과 개선 내용

### 1.1 원인

68차는 "원인 + 전망" 질문만 코드 경로(`_answer_forecast` → `answer_cause`)로 보냈다. 원인만 묻는 질문은 그대로 LLM 도구 호출 경로였다.

1. 모델은 원인 질문에 `news_tool`만 부른다. 이 도구는 이 종목의 **최근 기사 5건**을 준다. 시세 기준일과는 관계가 없다.
2. 코드가 `stock_tool`을 덧붙이지만 순서가 문제였다. 도구 결과 메시지는 호출 순서대로 붙는다.
   그래서 **시세 기준일을 알기 전에 기사가 LLM 컨텍스트에 들어갔다.**
3. 저장 시세가 늦으면(지금 개발 DB는 11-12에서 멈춤) 최근 기사는 전부 기준일 뒤다. LLM은 그 기사로 원인을 지어냈다.
4. 종목이 둘이면 `stock_tool`을 덧붙이지 않았다(`_add_requested_tools`는 종목 하나일 때만). 그래서 기준일 자체가 없었다.
5. 68차 원인 단락에도 빈틈이 있었다.
   - 기준일 당일 기사를 그날 자정까지 모두 후보로 넣었다. 장 마감(15:30) 뒤 기사도 들어갔다.
   - 기준일 당일 접수 공시도 들어갔다. 공시는 접수 시각이 없다.

### 1.2 기준 시점 규칙(`app/answer_cause.py`)

- 기준 시점 = 시세 기준일의 정규장 마감이다. `krx_calendar.close_time`을 쓴다(보통 15:30, 2026-11-19 수능일은 16:30).
  - `cutoff_at(base)`
  - `time_state(value, base, date_only)` → `before` / `after` / `unknown`
- 발행 시각이 마감 **전**이어야 후보다. 마감 시각 정각 이후는 그날 종가에 반영되지 않은 것으로 본다.
- 시각을 모르는 자료는 순서를 추정하지 않는다.
  - 실측(읽기 전용)
    - 공시 9,936건은 전부 KST 자정이다(접수일만 저장).
    - 뉴스 130,640건 중 KST 정각 자정은 135건이다. 날짜만 있는 행일 수 있다.
  - 기준일 **당일**의 이런 자료는 후보에서 빼고 건수만 밝힌다.
  - 기준일 전날까지의 자료는 날짜만으로 순서가 분명하므로 쓴다.
- 68차 `after_count`(기준일 다음 날부터의 기사 수)의 뜻은 그대로 두었다. 새로 센 값은 따로 둔다.
  - `after_close`: 당일 장 마감 뒤 기사
  - `unknown_news`: 당일 시각 모름 기사
  - `unknown_disclosures`: 당일 접수 공시

### 1.3 두 경로

| 경로 | 대상 | 방식 |
| --- | --- | --- |
| 코드 답(LLM 없음) | 원인 질문 + 종목 1개(없으면 직전 리포트 종목, 시장 질문은 제외) + 기간 없음·"오늘"·"어제"·"최근"·"요즘" | `_forecast_subject`의 새 모드 `cause`. 68차 `analyze`·`collect`·`section`을 재사용한다(새 원인 분석 로직 없음). 제목 줄에 시세 기준일, 기사 줄에 발행일을 쓴다 |
| LLM 경로 + 필터 | 그 밖의 원인 질문(두 종목, "한 달 동안"·"3개월간"·"이번 주" 같은 기간) | 모든 도구를 실행한 **뒤** `answer_cause.filter_records`가 `news_tool`·`disclosure_tool`·`rag_search_tool` 결과에서 기준 시점 뒤·당일 시각 모름 자료를 지운다. 그다음 tool 메시지를 만든다 |

LLM 경로 보완 사항

- 지운 자리는 기준 시점 전 자료로 다시 채운다.
  - `news_tool`·`disclosure_tool`에 내부 전용 인자 `before_kst`를 더했다.
  - LLM 도구 스키마에는 없다. `_run_tool`이 LLM 인자에서 지운다.
  - 공시는 기준일 0시 전(전날까지)만 다시 읽는다.
- 남은 자료가 없으면 결과를 `found: false`로 둔다. 메시지는 "…전까지 나온 관련 자료를 찾지 못했습니다. 원인을 특정할 수 없습니다."다.
- 지운 결과에는 `cause_cutoff`(기준일·마감 시각·뺀 건수·안내)를 붙인다.
  - 안내 문구는 보조 수단이다. 근거 차단은 위 필터가 한다.
- 출처 목록(`sources`)은 거른 결과로 만든다. 그래서 기준일 뒤 기사가 출처에도 남지 않는다.
- 여러 종목 원인 질문은 `_add_cause_price_tools`가 종목마다 `stock_tool`을 덧붙인다. 그래야 종목별 기준일로 거를 수 있다.
- 종목 정합성
  - 종목별 기준일은 각 종목의 `stock_tool` 결과에서 가져온다. ETF와 주식이 섞인 `rag_search_tool` 결과도 항목의 `company_names`로 그 종목의 기준일을 쓴다.
  - 다른 종목·이름이 비슷한 ETF 기사 제외는 68차와 같다(`news_relevance.evidence_news`: 제목 일치, ETF는 더 긴 다른 ETF 이름 제외).

"오늘"·"어제"

- "어제"는 오늘 전의 마지막 거래일이다(월요일의 어제 = 금요일).
  - 저장 시세가 그 뒤까지 있으면 시세를 그날까지로 잘라 같은 지표 계산을 쓴다(`analyze(rows=...)`).
  - 그러면 근거 창의 끝도 그날이 된다.
- 요청한 날의 시세가 없으면 다른 날을 그날인 것처럼 답하지 않는다. "…시세는 아직 저장되지 않아(미수집) 마지막 저장 거래일 X 기준으로 답합니다"라고 밝힌다.

## 8. 비공개 GitHub 저장소 방식의 실현 가능성

**판정**: 기술적으로는 가능하다. 그러나 **원천의 수집·저장 허용이 확인되지 않아 만들지 않았다.**

- 비공개로 옮겨도 공개 범위 문제만 줄어든다. 수집·저장 권한이 생기지는 않는다.
- 아래는 허용이 확인된 경우의 설계다.

| 항목 | 설계 |
| --- | --- |
| 1. 비공개 저장소 생성 | 이 작업 환경에는 `gh`도, 저장소를 만들 수 있는 토큰도 없다. 자동 발급 `GITHUB_TOKEN`은 저장소를 만들 수 없다. **사용자가 GitHub 웹에서 직접 만들어야 한다**(예: `lab-scale-minute-archive`, Private). 새 토큰은 만들지 않았다 |
| 2. 수집 코드 가져오기 | 비공개 저장소 workflow에서 `actions/checkout`으로 공개 저장소 `SeoYoonLim/lab-scale`을 **고정 커밋 SHA**로 받는다. 공개 저장소라 토큰이 필요 없다. 코드는 복사하지 않아 한 곳에서만 고친다 |
| 3. PAT 없이 `GITHUB_TOKEN`만 | 아티팩트 목록·내려받기·업로드는 모두 workflow가 있는 저장소(비공개 쪽) 안에서 일어난다. `permissions: {contents: read, actions: read}` + `actions/upload-artifact`로 충분하다(68차 구조 그대로). 공개 저장소에 쓸 일이 없다 |
| 4. 68차 엔진 재사용 | `python -m scripts.run_actions_minute_preservation run/verify`를 그대로 부른다. 350종목 목록·SHA-256 봉인·재다운로드 검증·중복 방지·용량 기준(60%/80%)이 같다. 비공개 저장소에서만 `RAW_UPLOAD_ENABLED: "true"` |
| 5. 기존 공개 아티팩트 이전 | 다른 저장소의 아티팩트는 `GITHUB_TOKEN`으로 못 읽는다(토큰 범위가 자기 저장소). 방법은 둘이다. (a) 사용자가 공개 저장소 아티팩트를 직접 내려받아 비공개 저장소에 올리는 일회성 수동 작업(PAT 없이 하려면 브라우저 다운로드 + 비공개 저장소 dispatch 입력 파일 업로드가 번거롭다). (b) 이전하지 않고 만료(12-17)를 기다린다. 원본 7일분은 원천이 다시 주지 않는다. 내부 보관 허용이 확인되지 않았으므로 **(b)를 권한다** |
| 6. 업로드 성공·SHA-256 재검증 | 68차 `verify` 단계 그대로(업로드 직후 API로 다시 받아 파일별 SHA-256 대조) |
| 7. 공개 아티팩트 정리 | 6.1 절차. 비공개 쪽 검증이 끝난 뒤에만 공개 쪽을 지운다 |
| 8. 30일 보관·용량 | `retention-days: 30`. 하루 zip 약 2.0~2.2MB × 30일 동안의 거래일 약 21일 = 약 45MB. 무료 계정 비공개 저장소 저장 한도 500MB(Packages 공유)의 약 9%. 68차 60%/80% 기준 유지 |
| 9. Actions 사용량 | 비공개 저장소는 실행 시간이 무료 한도에서 차감된다(9절·10절) |

## 10. Actions 비용과 용량 분석

- 근거: [GitHub Actions 과금 문서](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- 공개 저장소: 표준 GitHub-hosted runner는 무료이고, 포함 사용량에서 차감되지 않는다.
- 비공개 저장소(무료 개인 계정)
  - 월 포함 사용량은 분이 아니라 **$12 상당**으로 표시된다. Linux 2코어 $0.006/분으로 나누면 약 2,000분이다(문서 수치로 계산한 값).
  - 아티팩트 저장은 500MB(Packages 공유), GB-시간 단위로 쌓인다.
  - 결제 수단이 없으면 소진 뒤 실행이 막힌다. 결제 수단이 있으면 초과분이 청구된다.
- 비공개 저장소로 옮겼을 때의 추정(68차 실측 기반)
  - 68차 실측
    - 첫 실행 34분(7거래일 × 350 = 약 2,450회 요청, 1회 약 0.82초)
    - 두 번째 6분 34초(하루 350회 + 6일 검증)
    - 세 번째 47초(확인만)
  - 하루 2회 예약, 거래일 약 21일 기준
    - 본 실행(하루분 350회): 약 5~7분
    - 예비 실행(확인만): 약 1분
    - 하루 약 8분 × 21일 = **월 약 170분**. 포함 약 2,000분의 약 8~9%다
  - 단, 같은 계정의 다른 비공개 저장소가 쓰는 시간과 합산된다.
  - 실패 재실행·원천 지연이 겹치면 늘어난다. 첫 실행처럼 7일분을 받으면 한 번에 약 35분이다.
  - 저장: 약 45MB가 계속 유지되면 500MB의 약 9%다.
  - 무료 초과 위험은 낮다. 그래도 결제 수단을 등록하지 않는 편이 초과 청구를 막는 안전장치가 된다(초과 시 막힘).
- 현재(공개 저장소)
  - 분봉 실행은 없다. 실행 시간 비용도 0이다(공개 저장소 무료).
  - 저장소 아티팩트 합계는 약 17.7MB(159개, 대부분 CI `eval-offline-results` 약 30KB씩)다.
