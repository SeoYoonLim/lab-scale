# 최종 시연 전 AI 답변 정확성·종목 식별·다국어 오류 개선 (2026-11-21)

기준 main `a225a096eb9f231eccb3ce3f06c7fa908f31686b`, 브랜치 `fix/final-demo-answer-quality-20261121`(커밋·push 전).
새 기능이 아니라 기존 리서치 에이전트의 정확성·사용자 경험 수정이다. DB 마이그레이션·데이터 수집·package 파일 변경 없음.

## 1. 종목 식별

**재현으로 확인한 원인**(임시 DB + 실제 llama3.1:8b)
- 종목 없는 질문이 코드 답 경로에 걸리지 않으면 LLM 경로로 가는데, 모델이 질문에 없는 "삼성전자"를 도구 인자로 채웠다(도구 설명 예시 `예: 삼성전자, 005930`).
  해석되는 이름이라 기존 인자 보정(`_repair_company_args`)이 손대지 않았다. `"오늘 주가 어때?"` 1회차 삼성전자 조회, 2회차 미발견(비결정적).
- 직전 삼성전자 대화 뒤 `"엔비디아는 왜 하락했어?"`: 엔비디아가 등록 종목이 아니라 "이번 질문에 종목 없음"으로 보고 직전 질문의 종목(삼성전자)으로 인자를 바꿨다.

**수정**(`app/instrument_scope.py`, `app/agent.py`): 우선순위 = 이번 질문에 명시한 종목 > 유효한 직전 대화의 종목 > 되묻기
- 해외 미지원 종목(엔비디아·애플·테슬라 등 20개, 한·영·일·중 표기)을 말하고 등록 종목이 없으면 직전 대화가 있어도 대신 분석하지 않고 안내(`unsupported_instrument`).
- 후속 질문이 등록 종목에 없는 이름으로 시작하거나("롯데칠성은 …") 모델이 질문 속 이름을 그대로 넘겼는데 등록 종목이 아니면 직전 종목으로 바꾸지 않음(`unresolved_instrument`).
  주제어("외국인은", "배당은", "실적은" 등)는 종목 이름으로 보지 않는다.
- 종목도 직전 대화도 없고 질문이 일반어로만 되어 있으면 LLM에 보내지 않고 `어느 종목을 말씀하시는 건가요? 삼성전자, SK하이닉스 등 분석할 종목을 알려 주세요.`
- LLM 경로로 갔어도 질문에 흔적이 없는 종목 호출은 실행하지 않는다(오타 "삼성잔자"처럼 질문에서 온 것은 그대로).

**API**(하위 호환 추가, `POST /api/research`): `resolved_instruments`(`ticker`·`name`·`name_en`·`source`=explicit|previous_context),
`clarification_required`, `clarification_reason`. 프런트는 답변 위에 `분석 기준: 삼성전자 (005930)` / `Analysis based on: Samsung Electronics (005930)`.

## 2. 영어 질문

기존 구조(규칙 기반 질문 정규화 `app/intent_i18n` → 한국어 판정·도구·코드 계산 → 답만 번역)를 유지했다. LLM으로 질문을 번역하지 않으므로
종목명·숫자·기간이 번역 중 바뀌지 않는다. 빠져 있던 과거 원인 의도(`Why did … fall/rise`, 일·중 표현)를 `(왜 떨어졌어)`/`(왜 올랐어)`로 정규화하고,
주어가 대명사("Why did it fall?")면 직전 종목을 이어받을 수 있게 했다. 되묻기·미지원 안내는 언어별 고정 문장(`translation_status=localized`).

## 3. 답변 품질

- 최고·최저·현재가(`app/answer_extremes.py`, `guard_answer` 앞단): 최고·최저가 뒤바뀜·값·날짜 불일치, 저장 종가를 "현재가/실시간/오늘 종가"로 쓴 문장을
  도구 결과로 만든 결정론적 문장으로 바꾼다. 데이터가 없으면 그 문장을 지운다. LLM 재호출·추측 없음.
- 내부 문구: 도구 오류 원문(예외·SQL·"호출에 필요한 인자가 없습니다: limit")을 LLM에 넘기기 전에 일반 문장으로 바꾸고(`_llm_safe_result`),
  최종 답변에서 내부 오류·필드 이름·호출 인자·DB 테이블 이름이 든 문장만 지운다(`answer_tidy.has_internal_leak`). 일반 영어 "price limit" 등은 유지.
- 출처 없는 원인 절(LLM 경로): 뉴스·공시 출처가 없는데 "원인"이 든 절 제목("## 원인 분석", "## 하락 원인", "**원인 분석**" 등)을 쓰면
  그 절을 근거 없음 안내로 바꾼다(시장 비교 수치 문장만 "## 시장과 비교"로 남김). 원인 코드 경로(app/answer_cause)의 "주가 움직임과 원인" 절은
  출처가 없으면 그 절 안에서 "원인을 특정할 수 없습니다"라고 밝히는 기존 문장이라 바꾸지 않았다.
- 코드 요약에서 두 종목 뉴스에 같은 기사가 걸리면 한 번만 쓴다(반복 정리가 날짜만 남기던 문제).

## 4. 오류 코드

`{"detail": "기존 문장 그대로", "code": "INSUFFICIENT_HOLDINGS"}`. 코드: `INSUFFICIENT_HOLDINGS`, `INSUFFICIENT_CASH`, `INVALID_ORDER_QUANTITY`,
`UNSUPPORTED_ORDER_TYPE`, `INVALID_ORDER_REQUEST`, `STOCK_NOT_FOUND`, `PRICE_UNAVAILABLE`, `ALREADY_IN_WATCHLIST`, `NOT_IN_WATCHLIST`,
`RESET_CONFIRM_REQUIRED`, `AUTHENTICATION_REQUIRED`, `INVALID_CREDENTIALS`(`backend/API.md` "오류 코드(code)"). 프런트: 한국어 화면은 서버 문장 그대로,
다른 언어는 code 문구, 모르는 code·code 없는 한국어 문장은 상태 코드별 일반 문구(`frontend/src/api/errorMessages.ts`).

## 5. 주말 환율·데이터 시점 (우리 쪽 코드 수정 없음, 파트너 확인 필요)

읽기 전용 조사(11-18 공유 덤프를 임시 컨테이너에 복원한 사본. 운영 DB·수집기 미사용, 외부 원천 호출 없음).
- 사본의 USD/KRW: 월~목 각 30~31행, **금 1행, 토 1행(2026-10-31), 일 29행**(2026-04-05~10-18). 금요일이 거의 없고 일요일에 몰려 있다.
- 수집 코드 `app/collectors.py fetch_and_save_exchange_rate`는 `fdr.DataReader("USD/KRW")`의 날짜를 `idx.date()`로 그대로 저장한다. FinanceDataReader는
  이 쌍을 Yahoo(`KRW=X`)로 받고 날짜를 `pd.to_datetime(timestamp, unit="s").normalize()`, 즉 **UTC 날짜**로 자른다. Yahoo 환율 일봉은 런던 자정에 시작하므로
  영국 서머타임 기간(~10-25)에는 월요일 봉이 일요일 23:00 UTC → 일요일 날짜, 금요일 봉이 목요일 날짜가 된다(사본 분포와 서머타임 종료 뒤 금요일 행이 생긴 것이 일치).
  토요일 10-31 행은 토요일 오전 수집 시 원천이 준 행으로 보이나 외부 원천을 부르지 않아 **확인하지 못했다(추정)**.
- 저장 전 검증 `ingest_validation.check_fx`는 "출처가 일요일 날짜에도 값을 준다(실측), 주말 날짜를 격리하지 않는다"는 이전 판단으로 주말 행을 통과시킨다.
- 서비스 읽기 쪽(브리핑·전망 환율 요약·`/api/status` 환율 최신일)은 저장된 날짜를 그대로 쓴다. 읽기 쪽에서 주말 행을 거르면 실제로는 월요일 값인 일요일 행을 버리게 되므로
  읽기 쪽은 고치지 않았다. 고칠 곳은 수집 단계의 날짜 정규화다.

**파트너 요청 사항**
1. 운영 수집 환경이 이 저장소의 `fetch_and_save_exchange_rate`(FinanceDataReader → Yahoo)를 그대로 쓰는지, 다른 원천인지 확인.
2. 원천 날짜의 시간대 처리: Yahoo 일봉 timestamp를 UTC 날짜로 자르지 말고 거래일(런던 또는 서울 영업일 기준 중 정책 결정)로 정규화. 서머타임 경계(3월 말·10월 말) 포함 검증.
3. 저장 전 필터 정책: 토·일 날짜 행을 허용할지(원천이 실제로 주말 거래 값을 주는지) 결정하고, 허용하지 않으면 `check_fx` 단계에서 격리.
4. 기존 행 처리 방침: 이미 저장된 일요일 행(실제 월요일 값으로 추정)·토요일 행을 날짜 보정할지, 재수집할지, 그대로 둘지 결정(이번 작업에서는 변경하지 않음).
5. 보정 후 평일 최신 환율 기준일과 서비스 표시(`/api/status`의 환율 최신일, 브리핑 환율 기준일)가 일치하는지 확인.

## 6. 검증

- 백엔드 단위·통합·오프라인 평가, 프런트 tsc·lint·Vitest·build·audit: 결과 표는 작업 보고(채팅)에 있다.
- 독립 테스트 서버(127.0.0.1:8030, 11-18 덤프 사본, 실제 Ollama)로 핵심 질문 E2E: 시연 서버(8010·5173)·8000·운영 DB는 사용하지 않았다.
- 실제 브라우저 화면 확인은 하지 않았다(배지·오류 문구는 Vitest 렌더링 테스트로 확인).
- 남은 한계: 해외 종목 목록은 20개 고정이라 목록 밖 해외 종목은 기존 "종목을 찾지 못했습니다" 경로다. 후속 질문 첫 낱말 판정은 주제어 목록 밖 낱말을 종목 이름으로 볼 수 있다
  (이때도 다른 종목으로 대신 분석하지 않고 되묻는다).
