## 0. 한 줄 결론과 44차 대비 바뀐 점

- 44차 공식 종가 모드를 그대로 개발 DB에 쓰면 안전하지 않았다. 세 가지 결함을 고쳤다.
  1. 네이버 일별 시세를 600거래일에서 끊어 읽었다. ETF 앞부분이 옛 값으로 남는다.
  2. ETF 최신일을 장중에도 저장했다.
  3. **실제 종가로 덮어써 원천(FDR)의 수정주가 체계를 깨뜨렸다.** 엘앤씨바이오 2026-09-14에 +93% 가짜 급등이 생기고, 저장 전 검증이 일부를 격리해 기준이 섞였다.
- 저장 기준을 **"공식 종가를 원천의 수정주가 체계로"**로 바꿨다. 저장 종가 = 공식 종가 × (FDR 종가 ÷ 네이버 실제 종가).
  - 주식은 애프터마켓 차이만 고친다.
  - ETF는 애프터마켓 대상이 아니라 결과가 원천 값 그대로다. **44차의 "ETF = 실제 종가"는 취소한다.**
- 개발 DB 적용 시 예상: 주식 9,749행 변경(종가 9,053행), 1,500행 신규. ETF는 종가 변경 0행, 12행 변경, 300행 신규. 격리 0이다.
  백업 생성·복원·복구 절차를 검증했다. **실행 승인 대기.**

## 3. ETF 재수집 대상과 수정주가 처리 정책 [적용 준비 완료 / 결정 필요]

| 항목 | ETF 50종목(전 기간) |
| --- | --- |
| 저장 행 / 새 레코드 | 34,210 / 34,510 |
| 종가 변경 | **0** |
| 변경(그 밖) | 12(11-03처럼 수집 당시 미완성이던 거래량 등) |
| 신규 | 300(11-04~11-11) |
| 격리 / 경고 | 0 / 1(KODEX 레버리지 급변 경고, 저장은 됨) |
| 분배락일 | 460일 |

정책(권장): **저장 종가는 원천(FDR)의 수정주가 체계를 유지한다.** 근거는 다음과 같다(1차 계획에서 실제 종가로 덮어썼을 때 측정한 값).
- 실제 종가로 바꾸면 ETF 47종목의 250일 수익률이 중앙값 0.81%p, 최대 9.01%p 달라진다.
  분배락일마다 분배금만큼 "하락"으로 계산되기 때문이다. 커버드콜 ETF는 첫날 조정 계수가 0.77이다(누적 분배 약 23%).
- 저장 전 검증의 "기존 값과 충돌" 규칙이 커버드콜 ETF 3종목(차이 38~58%)을 격리한다. 그러면 일부 구간만 실제 종가로 바뀌어 **한 종목 안에 두 기준이 섞인다**.
- 주식도 같다. 엘앤씨바이오는 2026-10-26 기업 이벤트로 FDR이 과거를 0.5025배 조정했다. 09-14부터만 실제 가격으로 바꾸면 경계에 +93%가 생긴다.

화면 표시와의 관계:
- 차트·수익률은 같은 저장 종가를 쓴다. 따라서 과거 ETF 가격은 "분배 조정된 가격"으로 보인다(지금과 같음). 최근 분배락 이후 가격은 실제 종가와 같다.
- 실제 종가와 수정주가를 함께 보여 주려면 `adjusted_close` 열을 따로 두고 API 필드를 추가해야 한다. 스키마·API 계약 변경이므로 이번에는 하지 않았다 **[결정 필요]**.
- 남는 위험: FDR은 다음 분배락·기업 이벤트 때 과거 전체를 다시 조정한다. 수집 창(10~90일) 밖의 행은 옛 조정 상태로 남는다(41차 "수정주가 혼재"의 원인).
  대책 후보는 둘이다. 분배락·이벤트를 감지하면 그 종목 전 기간을 다시 받거나, 정기적으로 전 기간을 다시 받는다 **[결정 필요]**.

## 4. 백업과 복구 절차 [적용 준비 완료, 복원 검증함]

| 파일(`backend/backups/`, git 무시) | 크기 | SHA-256 |
| --- | --- | --- |
| `ai_investment_backup_20261111_192214_pre_official_close_prices_only.dump`(`stock_price`·`market_index` + 제약·인덱스) | 5,457,154 B | `fc49fae5…509b` |
| `ai_investment_backup_20261111_192214_pre_official_close_full.dump`(전체 DB) | 148,062,064 B | `1a183b0f…6476` |

검증한 것:
1. `pg_restore --list`: 두 테이블의 정의·데이터·PK·유니크·인덱스·FK가 모두 들어 있다.
2. **전체 백업 복원 시험**: 새 DB `ai_investment_restore_test`에 복원했다. `stock_price` 249,005, `market_index` 1,466, 사용자 2, 뉴스 17,853, 거래 3으로 개발 DB와 같다.
3. **복구 절차 시험**(같은 임시 DB): 11-03 종가 350행을 바꾸고 지수 2행을 지운 뒤 아래 명령으로 되돌렸다. 데이터 체크섬, 제약 5개, 인덱스 5개가 개발 DB와 같다.

```bash
docker cp backend/backups/ai_investment_backup_20261111_192214_pre_official_close_prices_only.dump ai_investment_db:/tmp/p.dump
docker exec ai_investment_db pg_restore -U postgres -d ai_investment --clean --if-exists --no-owner /tmp/p.dump
```

- 이 명령은 두 테이블을 지우고 다시 만든다. 그래서 실제 복구 때도 승인이 필요하다.
- **함정**: `pg_restore -t stock_price -t market_index`처럼 테이블을 지정하면 PK·유니크·인덱스·FK가 복원되지 않는다(시험에서 확인). 그러면 수집기 upsert가 깨진다. `-t` 없이 위처럼 쓴다.
- 임시 DB `ai_investment_restore_test`(개발 DB 사본)는 남겨 두었다. 필요 없으면 지우면 된다(사용자 판단).

## 7. `refresh_data` 기본 기준 전환 검토 [적용 준비 완료 / 결정 필요]

- 현재: 기본은 `source`다(FDR 그대로). 이번에 `refresh_data --close-basis {source,official}`를 추가했다(기본 `source` 유지, 단위 테스트 포함).
- 공식 종가 모드의 확정 시점:
  - 주식 d일의 공식 종가는 d+1일 행이 생겨야 복원된다. 그래서 **d일 장 마감 뒤 실행하면 주식 최신일은 d−1**이다.
  - ETF는 d일 15:30 뒤 실행이면 d일까지 저장된다. 장중에는 저장하지 않는다.
  - 지수(FDR 캐시)는 21:30~23:30 확정 갱신 전이면 d일이 장중 스냅숏이다.
- 실행 시각별 결과:

| 실행 시각(KST) | 주식 | ETF | 지수 | 화면 영향 |
| --- | --- | --- | --- | --- |
| d일 08:00~09:00 | d−2까지(NXT 아닌 종목은 d일 행이 아직 없음, 미확인) | d−1 | d−1 확정 | 주식만 하루 뒤짐 |
| **d일 09:10~13:00(권장)** | d−1 | d−1 | d−1 확정(캐시 23시 갱신분) | 기준일이 모두 d−1로 같다. 15:30 전 기대 거래일도 d−1이라 지연 0 |
| d일 15:40~21:00 | d−1 | d | **d 장중 스냅숏(미확정)** | 날짜가 섞인다(`dates_differ`). 지수가 틀림 |
| d일 23:30 뒤 | d−1 | d | d 확정 | 주식만 하루 뒤짐(지연 1 표시) |

- 권장: 기본을 `official`로 바꾸고 하루 1회 09:10~13:00에 실행한다. 자동 예약은 만들지 않았다 **[결정 필요]**.
- 장중 실행의 안전성: 주식 당일 행은 항상 미확정이라 쓰지 않는다. ETF 당일 행은 15:30 전에는 쓰지 않는다(45차 수정, 테스트 포함).
- API·화면: 응답 형식은 그대로다. 값만 바뀐다(주식 2026-09-14 이후). 프런트 변경은 필요 없다.
- NXT가 아닌 종목의 d일 행이 09:00 전 네이버 일별 시세에 생기는지는 장중에 확인하지 못했다(**미확인**). 그래서 권장 시각을 09:10 이후로 잡았다.

## 8. 지수 최신일 조사 결과 [결정 필요, 데이터 수정 안 함]

- 원천: FDR `KrxIndexReaderCache` → `raw.githubusercontent.com/FinanceData/fdr_krx_data_cache/.../data/index/year_ks11/{연도}.csv`(제3자 저장소).
- **갱신 시점**(저장소 커밋 이력, KST): 거래일마다 두 번 "auto-update"한다.
  - 13:30~15:00: 장중 스냅숏. 11-11 13:39, 11-10 14:54, 11-09 13:36 …
  - 21:30~23:30: 확정 갱신. 11-10 23:19, 11-09 22:20, 11-06 21:54 …
  - 11-11 13:39 행: 코스피 5,346.07, 거래량 151,964,072(평소의 약 60%). 확정값은 5,375.36(네이버 지수 일별·마감 기사)이다.
- 결과: 14시~21시에 지수를 수집하면 장중 스냅숏이 그날 종가로 저장된다. 검증 DB 11-11(15:40 수집)과 개발 DB 11-03(19:48 수집)이 그렇다.
  최신일을 뺀 과거 값은 FDR과 네이버가 같다(2025-09-01~).
- 화면: 지수 수집기(`app/collectors.py` `fetch_index_frame`)는 최신 행을 시각과 관계없이 저장한다. 시장 요약의 최신성(`app/market_snapshot.py`)은 날짜 지연만 본다.
  그래서 **장중 스냅숏도 "latest"로 표시된다**. 일일 브리핑·지수 대비 수익률도 같은 값을 쓴다.
- 해결 방향(검증 DB에서 먼저 시험할 것):
  - (a) 지수 수집을 23:30 뒤 또는 다음 날 오전에 한다(7절 권장 시각이면 해결된다).
  - (b) 수집 시각이 그날 23:30 전이면 지수 최신일을 다음 실행에서 다시 받고, 그때까지 "미확정"으로 표시한다(API 필드 추가는 합의 필요).
  - (c) 네이버 지수 일별 API로 최신 1~2일을 대조해 다르면 저장하지 않는다(네이버도 비공식 API).
- 개발 DB 11-03 지수(장중 값)는 이번에 고치지 않았다. 7절 권장 시각에 지수 단계를 다시 실행하면 같은 원천의 확정값(5,648.79, 네이버와 일치 확인)으로 upsert된다.

## 9. 개발 DB 적용 명령 [적용 준비 완료, 실행 승인 대기]

권장 실행 시각: 다음 거래일(2026-11-12) **09:10~13:00 KST**(7절).

```bash
cd backend
# 0) 실행 직전 백업을 새로 만든다(위 백업 이후 바뀐 게 있으면 그걸 기준으로 되돌리기 위해)
TS=$(date +%Y%m%d_%H%M%S)
docker exec ai_investment_db pg_dump -U postgres -d ai_investment -Fc -t stock_price -t market_index -f /tmp/p_$TS.dump
docker cp ai_investment_db:/tmp/p_$TS.dump backups/ai_investment_backup_${TS}_pre_official_close_prices_only.dump
# 1) 적용 전 상태 기록
python -m scripts.refresh_data --status --no-report
# 2) 주식: 2026-09-14 이후(창 75일이면 09-14를 포함한다). 오늘 행은 미확정이라 쓰지 않는다
python -m scripts.collect_prices --universe universe_top300.json --days 75 --close-basis official --delay 0.6 --report backups/official_stocks_$TS.json
# 3) ETF: 전 기간(2023-10-30~). 종가는 바뀌지 않고 미완성 거래량·신규 행만 반영된다
python -m scripts.collect_prices --universe universe_etf50.json --days 1110 --close-basis official --delay 0.6 --report backups/official_etf_$TS.json
# 4) 지수: 같은 원천에서 다시 받기(어젯밤 확정 갱신분). 원천 변경 없음
python -m scripts.collect_market_index --days 15
# 5) 적용 뒤 점검: 공식 종가 기대값과 다른 행 0, 중복 0, 하루 변동 30% 초과 0, 등락률 일치
python -m scripts.audit_close_basis --tickers 005930,000660,069500,102110,360750,290650,087010,472150 --since 2026-08-01 --dbs ai_investment --out backups/audit_after_$TS
python -m pytest -m "integration and not slow" -q
# 6) 백테스트 재생성(검토 뒤 커밋)
python -m scripts.backtest_outlook --collect backups/bt_$TS.npz && python -m scripts.backtest_outlook --final backups/bt_$TS.npz
```

- 예상 소요: 주식 약 4분, ETF 약 9분(네이버 요청 약 1,250회, 0.45~0.6초 간격), 지수 1분.
- 예상 변경: 2절·3절 표의 값이다. 실행 시점에 하루 더 지나면 신규 행이 하루치 늘어난다.
- 중복 방지: upsert(`uq_stock_price_company_date`)라 행이 중복되지 않는다. 삭제는 하지 않는다.

## 10. 실행 전 승인 필요 사항

1. **가격 기준 확정**: 저장 종가 = 공식 종가 × 원천 조정 비율(수정주가 체계 유지). 44차의 "ETF = 실제 종가"는 취소한다.
2. **개발 DB 적용**(9절 명령, 다음 거래일 09:10~13:00): 주식 9,749행 변경 + 1,500행 신규, ETF 12행 변경 + 300행 신규, 지수 재수집.
3. 복구 방식: 문제가 생기면 4절 명령으로 두 테이블을 백업 시점으로 되돌린다(테이블을 다시 만든다).
4. `refresh_data` 기본을 `official`로 바꿀지, 실행 시각을 09:10~13:00으로 할지. 예약 등록은 하지 않았다.
5. 지수 최신일 처리 방식(8절 a·b·c). `adjusted_close` 분리 여부. 분배락·기업 이벤트 뒤 전 기간 재수집 방식.
