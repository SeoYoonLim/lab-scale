# 프런트엔드 인수인계: 42차(2026-11-11) 통합 점검 결과와 실연동 테스트 정리 요청

대상: 프런트엔드 담당(서윤)과 팀. 기준: `origin/main` `6184514`(PR #1~#6 병합 후), 백엔드 수정 `feature/backend` `a6947ad`.
프런트 코드는 읽고 실행만 했다(고치지 않았다). 아래 "요청"은 프런트 쪽에서 판단해 고쳐 주면 된다.

## 1. 이번 차수에 바뀐 것(백엔드)

API 응답 모양·엔드포인트·필드는 **바뀌지 않았다**. 프런트 코드 변경은 필요 없다.

| 무엇 | 전 | 후 |
| --- | --- | --- |
| AI 전망 답의 "최근 N거래일" 최고·최저 종가 | N+1개 종가(수익률 비교 기준일 포함)에서 골랐다 | 기준일을 포함한 최근 N개 종가(주가 흐름 답과 같은 정의) |
| 같은 답의 "52주 기준 최근 250거래일" | 251개 종가 | 250개 종가 |
| 답 문장 "조회 기간 a~b, 최근 N거래일" | a~b가 실제로는 N+1거래일 | 정확히 N거래일 |

왜: 같은 종목·같은 "최근 20거래일"인데 전망 답과 주가 흐름 답의 최고·최저가 달랐다(2026-11-03 실제 DB 1주일 기간 350종목 중 91종목).
예: SK하이닉스 전망 답 최고 1,842,000원(10-02, 비교 기준일) vs 주가 흐름 답 1,784,000원(10-06). 지금은 둘 다 1,784,000원(10-06)이다.
리서치 답 본문(`answer`)을 그대로 보여 주므로 화면에서는 숫자만 바뀐다. 정의는 `backend/API.md` "기간 최고·최저 정의(통일)" 절.

## 2. 요청: `frontend/src/api/http.integration.test.ts`

실제 백엔드(`VITE_REAL_BACKEND=1`)에 붙여 돌린 결과 8개 중 7개 통과, 1개 실패했다.

### 2-1. `360750`을 "구성종목 미수집 ETF"로 가정한 단언(수정 필요)

- 위치: `it('공개 API: 상태·면책·종목·급등락·시세 차트·사건 반응·ETF 구성종목')` 안
  `const none = await httpApi.getEtfHoldings('360750', 5)` → `expect(none.items).toEqual([])`.
- 재현: 개발 DB(구성종목 수집됨)에 붙여 위 명령을 실행하면 `expected [ { rank: 1, code: 'NVDA US EQUITY', … } ] to deeply equal []`.
- 영향: 이 단언이 `it` 중간에 있어 **뒤쪽 검증(종목 뉴스·공시, ETF 공시 미지원, 365일 주가, 366일 422)이 실행되지 않는다.**
  42차에 이 한 줄만 임시로 빼고 돌리면 뒤쪽은 모두 통과했다(원본 파일은 그대로 두었다).
- 기대 동작: DB 상태와 관계없이 같은 결과가 나와야 한다. 예를 들어
  (a) "구성 데이터가 없는 ETF" 단언은 `items.length === 0`일 때만 `message`가 있는지 보거나,
  (b) 구성종목이 있든 없든 `items`가 배열이고 `message`/`items` 중 하나가 있다는 모양만 확인하거나,
  (c) 이 단언을 별도 `it`으로 떼어 실패해도 다른 검증이 계속 돌게 한다.
  어느 쪽이든 "수집 안 된 ETF"를 특정 종목코드로 고정하지 않는 편이 안전하다.

### 2-2. 임시 계정이 남는다(수정 필요)

- `beforeAll`의 `it…` 계정과 계정 복구 테스트의 `ac…` 계정은 끝나도 지워지지 않는다(탈퇴 테스트 계정만 지워진다).
  42차 실행 한 번에 3개가 남아 백엔드에서 탈퇴 API로 지웠다.
- 기대 동작: `afterAll`에서 각 계정을 `DELETE /api/auth/me`(`current_password` 필요)로 지운다.
  비밀번호를 바꾸는 테스트의 계정은 바뀐 비밀번호로, 로그아웃 테스트 뒤의 계정은 다시 로그인해서 지운다.
- 참고: 가입은 IP당 시간당 10회(`RATE_LIMIT_SIGNUP_PER_HOUR`)라 정리가 없으면 반복 실행 때 429가 먼저 난다.

### 백엔드에서 이번에 같이 고친 것: 간접 뉴스 시각 KST

`app/related_news.py` `indirect_news`가 시각을 UTC(`+00:00`)로 내보냈다. 일일 브리핑의 `holdings.items[].indirect_news.items[].published_at`과
`sources[].date`(간접 뉴스 항목)가 이 값이었다. 이제 다른 뉴스와 같이 KST(`+09:00`)다. 프런트가 `Date`로 파싱해 보여 줬다면 화면 시각은
같았을 것이고, 문자열 앞 10자를 날짜로 쓴 곳이 있다면 KST 00~09시 기사가 하루 전 날짜로 보였을 것이다.

## 5. 아직 남은 문제(확인 필요)

### 5-1. 차트 등락률과 실시간 시세 등락률이 다르다(원천 데이터, 최우선 확인)

2026-11-11 삼성전자: 실시간 시세 `+7,100원(+3.57%)`, 차트·리서치 답 `+4.41%`. SK하이닉스: 실시간·기사 `+65,000원(+5.36%)`, 차트 `+6.59%`.
11-11 종가는 셋 다 같고(206,000 / 1,277,000원) **11-10 종가가 다르다**: 저장값(FinanceDataReader 기본 소스 = 네이버 일봉) 197,300 / 1,198,000원,
실시간 기준가·여러 언론 보도 198,900 / 1,212,000원. 대체거래소(NXT) 애프터마켓까지 합친 통합 종가와 KRX 정규장 종가의 차이로 추정하지만
외부 근거로 확정하지 않았다. 확정되면 수집 시각 규칙(15:40 vs 20:00 이후)이나 소스를 정해야 하고, 그 전까지 종목 상세에서 두 숫자가 나란히 보이면
사용자에게 모순으로 보일 수 있다.

### 5-2. 그 밖

- TIGER 200 2026-11-02 등락률 +1.42%(다른 코스피200 ETF +2.2~2.4%): 오늘 다시 받은 원천 값과 같다(저장 오류는 아님). 원천 자체는 미확인.
- 중국어 번역에 한국어 조각이 섞인 문장이 `translated`로 통과했다(예: "半导体테스的基础设施"). 번역 검증기 보강 후보.
- KRX 거래일 달력이 2026-12-31까지다. 범위 밖 평일은 "열릴 수 있는 날"로 세므로 2027년 설 연휴부터 지연이 크게 잡힌다. KRX가 12월에 공지하면 추가한다.
- 개발 DB 데이터는 여전히 2026-11-03에서 멈춰 있고 자동 갱신 예약은 없다(등록 여부는 팀 결정).
- 그래서 개발 DB에 붙여 돌리는 `needs_collected_data` 통합 테스트 9개(전망 방향 4종)가 장 마감 뒤(지연 6영업일)부터 실패한다. 전망은 지연 5영업일 초과면 판단 유보라 설계대로다. 42차 수정 전 코드에서도 같은 9개가 실패하는 것을 확인했다. CI에서는 제외되는 묶음이다. 데이터 갱신 후 다시 본다.
