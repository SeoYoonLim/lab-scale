### 2.1 ETF 보유 종목 질문(문제 1)
원인:
1. 구성종목 게이트(`app/etf.py` `asks_constituents`)가 한국어 일부 표현만 알았다. "포트폴리오", "안에 뭐 들어있어", "비중 큰 종목", "1위 종목"과 영어·일본어·중국어 질문은 지나가지 못했다.
2. ETF 이름을 가리는 함수(`mask_etf_names`)가 뒤 단어까지 이름으로 보고 지웠다. 영문·숫자가 섞인 뒤 단어("holdings", "1위")와 띄어쓰기 없는 일본어·중국어("200の構成銘柄を教えて")가 사라졌다.
3. "KODEX 200에서 삼성전자 비중"처럼 특정 종목의 비중을 묻는 경로가 없었다. 두 종목 주가 비교 답이 됐다.
4. 구성종목 답(코드 템플릿)을 다른 언어로 보낼 때 LLM 번역을 거쳤다. 비중·종목코드가 수십 개라 검증에 떨어져 데이터 요약으로 바뀌었다.

수정:
- `asks_constituents`에 새 표현을 더했다(`_CONSTITUENT_MORE_RE`). 새 패턴은 "브랜드 + 첫 단어"까지만 가린 문자열에 적용한다(`_mask_etf_heads`, 한중일 문자 앞에서 단어를 끊는다).
- 매매·배분 질문은 넣지 않는다: "비중 늘려도 돼?", "포트폴리오에 넣어도 될까?", "Should I keep holding…".
- `asks_holding_weight`(신규): ETF 하나와 주식이 함께 있고 비중·편입 여부를 물으면 전체 구성종목에서 그 종목의 비중·순위를 답한다.
  - 구성종목에 없으면 "종목은 없습니다"라고 답한다. 비중·순위·비교 질문("어떻게 나눠야 해?", "어느 쪽을 살까")은 해당하지 않는다.
  - 조회는 `etf_holdings_db.holding_weights`(종목코드 또는 이름으로 찾음), 문장은 `etf_holdings.holding_weight_answer`가 만든다.
- 언어별 템플릿 `app/etf_holdings_i18n.py`(신규):
  - 같은 데이터로 다시 만든 한국어 답이 실제 답과 글자까지 같을 때만 쓰고, 다르면 기존 보호 번역으로 넘긴다.
  - 숫자·날짜·종목코드·종목명은 데이터 값 그대로다. 출처 이름·기한 경과 안내·비중 합계 경고·레버리지 안내는 언어별 문장으로 옮긴다.
  - 데이터는 에이전트 내부 meta(`etf_holdings`)로 번역 단계에 넘긴다. API 응답과 `used_tools`에는 나가지 않는다.

테스트 `tests/test_etf_holdings_round48.py`(65개):
- 게이트: 새 표현 22개. 수정 전 21개 실패(나중에 추가한 1개 포함 22개)이고, 반례 10개는 수정 전후 모두 False다.
- 비중 게이트와 반례, 비중 답 문장, 에이전트 라우팅. LLM을 부르면 실패하도록 만든 끝단 테스트가 일본어 질문 → `localized` 답을 확인한다.
- 언어별 템플릿: 숫자 집합이 한국어 답과 같고, 이름 밖에 한국어가 없다. 레버리지·기한 경과 안내, 답이 다르면 `None`.

### 2.2 기준일·데이터 기준 시점(문제 2)
원인:
1. 기준일 안내(`freshness_note`)는 "오늘·지금" 시세 질문에서 데이터가 2영업일 이상 늦을 때만 붙었다. 어제 종가처럼 최신 데이터의 날짜는 LLM이 쓰지 않으면 빠졌다.
2. "삼성전자 분석해줘"에 모델이 `news_tool`만 불렀다(주가 없음).

수정:
- `app/answer_basis.py`(신규) `ensure_basis`: LLM 답에 시세 도구 결과가 있는데 그 마지막 시세 날짜가 없으면 표준 한 줄을 붙인다.
  - 문구는 단순 시세 답과 같다: `데이터 기준일: YYYY-MM-DD 종가(DB에 저장된 종가이며 실시간 시세가 아닙니다).` + 지연이면 지연 안내(`app.quote_freshness.line`).
  - 날짜는 ISO·점·한국어 표기를 인정한다. 다른 날짜(기간 최고가 날 등)는 인정하지 않는다. 종목마다 날짜가 다르면 종목별로 쓴다.
  - 뉴스·공시만 쓴 답이 날짜를 하나도 말하지 않으면 참고한 게시일 범위를 붙인다.
- `routing.is_analysis_question`(신규, 4개 언어): 분석·상태 질문이면 `_add_requested_tools`가 `stock_tool`을 덧붙인다. 원인 질문과 같은 방식이며, 호출 종목이 하나일 때만 붙인다. "뉴스 요약해줘"는 해당하지 않는다.
- 코드 템플릿 답(전망·주가 흐름·시세 등)에는 붙이지 않는다. 이미 기준일이 있고, 언어별 템플릿의 "글자까지 같음" 조건을 깨지 않기 위해서다.

테스트 `tests/test_answer_quality_round48.py` 기준일 부분 24개(수정 전 모듈 없음 → 전부 실패).
기존 테스트 중 바뀐 것:
- 날짜 없는 가짜 LLM 답 2건: 기대값에 기준일 줄을 더했다(본문은 그대로).
- 도구 덧붙임 말뭉치(622문항) 중 3문항: 분석 질문이라 `stock_tool`이 추가된다.

### 2.3 근거 없는 일반론·반복(문제 3)
원인: LLM이 도구 결과와 무관하게 어느 종목에나 붙는 문장을 썼다. 기존 반복 제거는 글자까지 같은 문장만 지웠다.

수정: `app/answer_tidy.py` `strip_generic`(신규, `_guard`에서 숫자 검증·서술 검증 뒤에 실행). 지우는 것은 다음뿐이다.
- 숫자가 없고 정해진 상투 표현이 든 문장. 예: "다양한/수많은 요인에 의해", "일반적인 기업의 주가와 마찬가지로", "이러한 요인을 함께 고려", "투자는 신중하게", "전문가와 상담", "향후 주가를 지켜봐야".
  면책 안내는 응답의 `disclaimer` 필드로 따로 나가므로 사라지지 않는다.
- 도구 이름(`stock_tool` 등)이 드러난 문장.
- "원인 분석" 절에서, 숫자가 모두 앞 절에 이미 나왔고 원인을 가리키는 낱말(뉴스·공시·계약·시장·때문 …)이 없는 문장.
- "다음과 같습니다"만 남은 절의 안내 문장, 글머리 기호만 있는 줄, 본문 없는 제목(이제 반복이 없어도 지운다).
- 다 지워지면 도구 결과가 있을 때는 코드 요약, 없으면(개념 답 등) 원래 글을 그대로 둔다.

테스트: 같은 파일 일반론 부분 11개. 입력은 기준선 실답 원문이다(d05·e01·g01, holdout D3). 데이터 문장·구체적 원인·레버리지 안내는 남는지도 확인한다.

### 2.5 숫자가 많은 문단의 번역(문제 5)
원인: 숫자를 바꾼 경우는 없었다(LLM은 자리표시자만 보고 코드가 값을 되돌린다). 실패는 형식이었고, 한 문단만 실패해도 답 전체가 데이터 요약이 됐다. 기준선 36문항에서 10건이다.
- 괄호 훼손: "⟦2⟧원" → "⟦2⟩円"
- 섹션 제목을 옮기지 않음("## 주가 동향", "## 관련ニュース"): 가장 흔했다
- '하루'를 "1日"로 옮겨 원문에 없는 숫자가 생김
- 자리표시자 번호를 숫자로 풀어 씀("⟦10⟧" → "10")

수정(`app/i18n_translate.py`):
- 괄호만 바뀐 자리표시자는 번호가 원문에 있을 때만 되돌린다(`repair_tokens`). 숫자만 쓴 경우는 고치지 않고 거절한다.
- 정해진 섹션 제목(주가 동향·원인 분석·뉴스·공시 근거·관련 뉴스·관련 공시·시장 상황·위험요인)은 코드 사전으로 옮긴다(`HEADINGS`).
- 프롬프트 전용 표현 힌트(`PROMPT_HINTS`: 하루 → 当日/that day/当日). 프런트 리소스와 동기화되는 `FINANCE_TERMS`는 바꾸지 않았다.
- 문단이 두 번 실패하면 줄 단위로 다시 옮긴다(`_translate_lines`). 줄도 같은 검증을 통과해야 하고, 한 줄이라도 실패하면 전과 같이 데이터 요약이다.
- 구성종목 답은 번역하지 않고 언어별 템플릿으로 보낸다(2.1).

테스트 `tests/test_i18n_numbers_round48.py`(9개, 가짜 LLM): 수정 전 7개 실패. 숫자 변형·번호를 숫자로 쓴 경우는 수정 전후 모두 거절한다.
기존 `tests/test_i18n.py`의 호출 횟수 단언 1개를 "MAX_ATTEMPTS 이상 + 줄 단위 시도 기록"으로 바꿨다(줄 단위 재시도 때문).

## 3. 4개 언어 실답 검사

하네스 `evals/run_multilingual.py`(신규, live 전용), 문항 `evals/multilingual_cases.txt`(57문항: dev 36 · holdout 21, ko·en·ja·zh).
- 실행 조건: 개발 DB는 읽기 전용 세션(`default_transaction_read_only=on`), Ollama `llama3.1:8b`(포트 13434, `OLLAMA_HOST`만 지정), `save_report=False`.
- 수정 전은 HEAD(`ff1309b`) 워크트리에서 같은 문항으로 쟀다.
- holdout은 수정을 마친 뒤 한 번만 돌렸다(수정 중 결과를 보지 않음).

| 실행 | 문항 | 종목 오매칭 | 출처 ID 없음 | 숫자 변형 | 기준일 누락 | 구성종목 없음 | 번역 실패(데이터 요약) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| dev 수정 전 | 36 | 7 | 0 | 0 | 2 | 10/10 | 10 |
| dev 수정 후 | 36 | 0 | 0 | 0 | 0 | 0/10 | 3 |
| holdout 수정 전 | 21 | 7 | 0 | 0 | 2 | 6/6 | 3 |
| holdout 수정 후(공식) | 21 | 1 | 0 | 0 | 0 | 1/6 | 4 |
| 전체 재확인(holdout 뒤 수정 4건 포함) | 57 | 0 | 0 | 0 | 0 | 0/16 | 6(dev 2 · holdout 4) |

- holdout 수정 후 남은 2건은 수정 후 고쳤다(2.1 영어 "Which companies", 2.4 "현대모터스"). 고친 뒤 결과는 재확인 행이다. 개선 주장은 공식 holdout 행으로 한다.
- 번역 실패는 dev에서 10→3으로 줄었지만 holdout에서는 3→4로 줄지 않았다.
  - holdout의 새 실패 D3·D4·N3은 수정 전에는 주가를 조회하지 않거나(D3·D4) 종목이 달라(N3) 짧은 답이었다.
  - 수정 후 답이 길어지고(주가 문단 + 기준일 줄) 번역할 문장이 늘었다. 같은 모델의 비결정성도 크다.
  - 실패해도 한국어 원문이나 틀린 숫자는 나가지 않는다(그 언어 안내 + 데이터 요약). 번역 후 숫자 변형은 모든 실행에서 0이다.
- 수정 전 하네스의 오탐 2종(한국어 날짜 표기, 공시 `source_url`)은 고친 하네스 기준으로 다시 채점했다.

## 4. 설계 원칙 준수
- 숫자 계산은 코드가 한다. 새로 생긴 숫자는 모두 DB 조회값이다(구성종목 비중·순위, 기준일). LLM은 숫자를 만들지 않는다.
- 근거가 부족하면 추측하지 않는다:
  - 구성종목 데이터가 없는 ETF는 기존 "제공하지 않음" 답이다.
  - 구성종목에 없는 종목은 "없습니다"다.
  - 모호한 외국어 표기("三星")는 종목을 고르지 않는다.
- API 계약은 그대로다: 요청·응답 필드, `used_tools` 값 목록, `translation_status` 값 목록. 프런트 코드는 바꾸지 않았다.
- 한국어 답: 기존 단위 테스트 5,640개와 CI 오프라인 평가(오매칭 0 게이트·품질 평가, 실패 11건 = 기존 "의도된 거절" 목록 그대로)가 통과한다.

## 5. 미해결 문제
1. **번역 실패 → 데이터 요약**: dev 3/36, holdout 4/21, 전체 재확인 6/57(매 실행 건수와 문항이 달라진다). 원인은 llama3.1:8b가 긴 답에서 자리표시자·형식을 지키지 못하는 것이다. 다음 후보: 줄 단위 번역을 처음부터 쓰기(호출 수 증가), 번역 전용 소형 모델 비교(모델 설정 변경이라 승인 필요).
2. **기사 속 옛 시세가 "주가 동향"에 섞임**(holdout D4):
   - "30일 KRX 마감 기준, LG전자 주가가 147,800원"은 뉴스 본문의 숫자라 숫자 검증을 통과했다. 그런데 표준 기준일 줄(11-12)이 함께 붙었다.
   - 기사 수치를 시세처럼 쓰는 문장은 ETF 답에서만 막고 있다(`news_result_for_llm`). 주식 답에도 적용할지 결정이 필요하다.
3. **일반론 제거는 정해진 표현 목록 방식**이다. 목록 밖의 새 상투 표현은 남는다. 실답 검사 지표에는 아직 "일반론" 항목이 없다(판정 기준을 정한 뒤 추가 후보).
4. **외국어 종목명은 86종목**이다. 나머지 264종목은 한글·영문 등록명·기존 별칭으로만 찾는다. 확신이 없는 중국어 음차(예: 셀트리온, 고려아연)는 넣지 않았다.
5. **질문 의도 판정은 아직 한국어 중심**이다. 구성종목·분석 게이트만 4개 언어로 넓혔다. 기간 표현("最近20个交易日"), 전망·시세 같은 다른 게이트는 한국어만 본다. 외국어 질문은 그만큼 LLM 경로로 간다.

## 6. 프런트엔드와 공유할 변경 사항
API 요청·응답의 모양은 바뀌지 않았다(새 필드 없음). 바뀐 것은 아래 답변 문장과 일부 상태값의 빈도다. 프런트에서 고칠 것은 없다.

| 상황 | 이전 | 지금 |
| --- | --- | --- |
| "KODEX 200 포트폴리오 알려줘", "What are the top holdings of KODEX 200?", "KODEX 200の構成銘柄を教えて", "KODEX 200的成分股有哪些？" | 주가·뉴스 LLM 답(`used_tools`: `stock_tool`, `news_tool`) | 구성종목 템플릿(기존 "KODEX 200 구성종목 알려줘"와 같은 답). `used_tools`는 빈 배열, `sources`도 빈 배열 |
| "KODEX 200에서 삼성전자 비중은 얼마야?"(4개 언어) | 두 종목 주가 비교 | "KODEX 200에서 삼성전자(005930)의 비중은 34.19%입니다. … 201개 구성종목 중 1위 …" + 기준일·출처. 없으면 "… 종목은 없습니다". `used_tools` 빈 배열 |
| 위 두 답의 en/ja/zh | LLM 번역(자주 `fallback_summary`) | 언어별 템플릿, `translation_status` = `localized` |
| 날짜 없이 시세를 말한 LLM 답 | 날짜 없음 | 끝에 `데이터 기준일: YYYY-MM-DD 종가(DB에 저장된 종가이며 실시간 시세가 아닙니다).`(단순 시세 답과 같은 줄, 번역되면 그 언어) |
| "삼성전자 분석해줘", "How is SK hynix doing?" | 뉴스만 조회할 때가 있었음 | `used_tools`에 `stock_tool`이 항상 들어간다 |
| 일본어·중국어·영어 종목명 질문 | 종목 없음 또는 다른 종목 | 국내 종목으로 해석. 답의 종목명은 기존 정책대로 한국어 등록명 원문 |
| 번역 답의 섹션 제목 | LLM이 옮김(가끔 한국어가 남아 `fallback_summary`) | 코드 사전 고정: en "Price Trend"·"Cause Analysis"·"News and Filings"… / ja "株価動向"… / zh "股价走势"… |

- `translation_status`: `localized` 비율이 늘고 `fallback_summary`가 줄었다(dev 10→3). 값 목록은 그대로다.
- 답 본문에서 "투자는 신중하게" 같은 LLM 상투 문장이 빠진다. 면책은 지금처럼 `disclaimer` 필드로 보여 주면 된다.
